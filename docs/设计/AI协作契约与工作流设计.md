# AI 协作契约与工作流设计

状态：设计稿 v1，2026-11-23。

**适用范围：** 开发阶段，团队成员和各类 AI agent（Codex、Claude Code、Antigravity、DeepSeek Harness 等）在同一个 GitHub 仓库上协作。产品内部的 agent 工作流不在本文范围，见 `单一模型Agent工作流设计.md` 和 `设计修订v2.md`。

**仓库：** `mcjiansheng/AIExamPrepAssistant`，本机克隆在工作区的 `AIExamPrepAssistant/`（2026-11-23 时还没有提交）。

**依据：** Harness 工作流指引（Trackmind 原文，加上「同行 Journey」应用时的修正）。配套的仓库文件（AGENTS.md、STATE.md、README、`.gitignore`、`docs/协作/` 模板）已放在仓库里。

## 0. 结论速览

| 项 | 决定 |
|---|---|
| 规则文件 | 仓库根目录只放 `AGENTS.md`，作为所有工具共用的唯一规则来源；**不建 `CLAUDE.md`**（见 2.3） |
| 状态文件 | 根目录 `STATE.md`，是快照不是日志；按工作线分条，各工作线只改自己的条目 |
| 仓库与本地 | 鸿蒙工程、设计文档、接口合同、实施记录进仓库；原型、交接文档、代跑报告、实验输出留在本地；课程资料和密钥任何时候都不进仓库 |
| 分支 | 每个任务一个分支；`main` 只通过 PR 合并，合并须人确认 |
| 完成标准 | 写在 AGENTS.md，分鸿蒙端、后端、接口三类；都要贴出实际运行结果 |
| 接口 | 先改合同，再改代码；改合同须另一端负责人确认 |
| AI 署名 | 提交信息不加 AI 署名；AI 参与情况记在 README「AI 参与说明」，各 AI 只维护自己那一行 |
| 暂不做 | 重试上限、失败分类、STATE.md 的脚本检查、鸿蒙端的 CI 构建 |

## 1. 现状与搭建级别

### 1.1 已经做到的

- **交接文档就是合同。** 原型目录的 `HANDOFF.md` 写了目标、禁止事项、用量上限、停下来问人的条件和报告格式，还写明代跑 agent 的职责是“运行和如实报告，不是让结果好看”。
- **规则来自真实事故。** 第 1 轮实验结果被 `--fresh` 删除 →“不用 `--fresh`、不覆盖 `out/`”；`| tail` 截断输出看不到结尾的 OK →“不要截断测试输出”；iCloud 读文件报错 →“遇到 iCloud 错误停下来问人”。
- **产品设计里的原则与指南一致。** “权限由代码判定”“能用程序判断的不交给模型”，就是指南的“危险动作靠机制拦，不靠一句话”。

### 1.2 缺口

1. **没有 AGENTS.md。** 地图散在进展总览、原型 README 和交接文档里，每接入一个新会话都要重新交代背景。
2. **状态和记录混在一起。** 进展总览既当索引又当状态；`设计修订v2.md` 的第 5 节是逐轮实验记录，设计文档正在变成日志。
3. **鸿蒙端没有完成标准。** 构建命令、模拟器验收、截图位置都没定。ArkTS 公开训练数据少，AI 容易编造 API 或“说完成其实没完成”。
4. **接口合同还没写。** 计划书里“先定接口”是前后端并行开发的前提，API 文档和 Schema v0.3 都还没有。
5. **两处高风险只靠文字拦。** 课程资料不能公开、密钥不能外泄，目前只写在交接文档里。进入 GitHub、多个 agent 都有推送权限后，需要落到机制上。

### 1.3 搭建到哪一级

按指南的 Level 0–3：

- **Level 1（地图 + 完成标准）：** 立即做。多个工具、多个人，已经出现“每次都要重复交代背景”的升级信号。
- **Level 2（STATE.md + 实施记录 + CI）：** 立即做。任务跨会话、跨工具，设计文档已经开始变成日志。CI 先只覆盖后端（见第 10 节）。
- **Level 3 提前做一项：** 课程资料和密钥的机制隔离（`local/` + `.gitignore`）。理由：指南检查清单建议第 7 项（危险动作靠机制拦）尽早做到；课程资料一旦推到远端就无法真正撤回，而且多个 agent 都能推送。
- **分支保护不做。** 本项目推送 `main` 不会触发部署，误推可以撤回，用 PR 加“合并须用户确认”就够了。出过一次直接推送 `main` 的事故再考虑开（公开仓库可以免费开）。
- **Level 3 其余（工具层审批配置、常规化独立验证）：** 等出现相关故障再加。

## 2. 参与方与分工

### 2.1 人

| 工作线 | 负责人 | 负责 |
|---|---|---|
| 鸿蒙端 | `<成员>` | ArkUI 页面、文件与权限、ArkWeb 试卷渲染、模拟器验收 |
| 后端与 AI | `<成员>` | API、资料解析、提示词、出题与校验 |
| 设计与评测 | `<成员>` | 设计、样例、评测、报告；审查合入 |

不管 agent 怎么换，以下三件事都由人批准：**合并到 `main`、修改接口合同、修改 AGENTS.md 的规则。**

### 2.2 Agent

| 角色 | 典型工具 | 工作位置 | 做什么 | 不做什么 |
|---|---|---|---|---|
| 编码 | Codex、Claude Code、Antigravity、DevEco 系工具 | 仓库，自己的任务分支 | 实现、跑检查、提交、推送任务分支、开 PR | 合并 `main`；未经确认改合同 |
| 本地代跑 | DeepSeek Harness 等 | 本地原型目录或 `local/` | 按交接文档用真实模型跑实验、写报告 | 改设计、改已有代码和数据、向仓库提交 |
| 设计 | Claude（claude.ai Project）等 | Project 文档、工作区 | 设计、写交接文档和合同 | 直接推送代码 |
| 验证 | 任一工具的新会话 | 只读，可以跑测试 | 按验证者提示词找拒绝的理由 | 审查自己写的改动 |

同一个工具可以担任不同角色，但**同一个改动的实现者和验证者不能是同一个会话**。

### 2.3 规则文件的兼容

- **只维护根目录的 `AGENTS.md`。** Codex 原生读取。Claude Code 从 2.1.277 版起，在没有 `CLAUDE.md` 的项目里会读 `AGENTS.md`。
- **仓库里不要建 `CLAUDE.md`。** 两个文件同时存在时，Claude Code 默认只读 `CLAUDE.md`，`AGENTS.md` 会被跳过。
- **不会自动读取 `AGENTS.md` 的工具（或旧版本）：** 在会话开头的提示词里写“先读仓库根目录的 AGENTS.md 和 STATE.md”。某个工具非要自己的文件名时，那个文件只写一行“见 AGENTS.md”，不写任何规则。
- **个人的工具配置**（全局习惯、快捷命令）放在各自用户目录，不进仓库。与 AGENTS.md 冲突时以 AGENTS.md 为准。

## 3. 仓库与本地的边界

| 位置 | 放什么 | 由什么保证 |
|---|---|---|
| 仓库 | 鸿蒙工程；产品后端（开始写时）；`schema/`；`docs/` 下的设计、项目计划、原型说明、评测、展示网页、接口合同、实施记录、协作模板；`AGENTS.md`、`STATE.md`、`README.md` | PR 合并 |
| 本地，不进仓库 | 仓库里的 `local/`：`课件资料/`、`api_key/`、`评测/`、`证据/`、`交接/`；仓库外的原型目录（`~/Documents/软件工程/exam-prep-prototype`）及其实验输出 | `.gitignore` 忽略 `local/` |
| 任何时候都不进仓库 | 课程资料原件、`*.sqlite`、上传文件、含课件内容的回归集；模型密钥；鸿蒙签名材料 | `.gitignore` + 密钥只从环境变量或 `local/api_key/` 读取。仓库是公开的（2026-11-24 用户确认），所以这两条是唯一的防线 |

**`local/` 的用途：** 仓库目录下的课件资料和 API key 只能放这里；文档里含课件原文或题目内容的，整份放这里，仓库只留数字和结论（例如回归评测报告：全文在 `local/评测/`，数字在 `docs/评测/README.md`）。另外放只属于本机的产出：交接文档、代跑报告、含真实课程内容的截图。原型目录和 `~/Documents/api_key/` 里的资料和 key 保持原位。

**本地成果怎么进仓库：** 代跑报告本身不进仓库，里面可能有课件原文。由设计方或负责人把结论和数字写进 `docs/实施记录/`，注明报告的本地路径和日期，不贴课件内容。

**截图：** 截图里有真实课程内容的只放 `local/证据/`；放进仓库的截图要用演示数据。

**文档类文件：** `.gitignore` 默认忽略 `*.ppt`、`*.pptx`、`*.pdf`、`*.docx`，因为课件和作业就是这些格式。确实需要提交时用 `git add -f`，并在 PR 里说明。这样提交这类文件必须是有意的。

## 4. 权限

| 档位 | 动作 | 由什么保证 |
|---|---|---|
| 直接做 | 读、搜索仓库；运行测试、构建、格式检查；在自己的任务分支修改、提交、推送；开 PR；在 `local/` 写文件；重写 STATE.md 中自己工作线的条目；更新 README 里自己那行 AI 参与说明 | 工具默认允许 |
| 先问 | 合并到 `main` | PR + AGENTS.md 写明 |
| | 修改接口合同（`schema/`、`docs/接口合同/`） | 单独 PR，另一端负责人确认 |
| | 修改 AGENTS.md 的规则、CI 配置、`.gitignore` 中资料和密钥的条目 | AGENTS.md 写明 + PR 审查 |
| | 新增或升级依赖；删除文件、目录或分支 | AGENTS.md 写明 |
| | 超出任务给定用量的真实模型调用 | 交接文档写明上限 |
| | 修改设计文档里已经定下来的结论 | AGENTS.md 写明 |
| 禁止 | 直接推送 `main`；强制推送共享分支 | AGENTS.md 写明（出过事故再开分支保护） |
| | 提交课程资料、数据库、密钥、签名材料 | **`local/` + `.gitignore`**（仓库公开，推送即公开） |
| | 打开、输出或转述密钥文件 | 密钥只放 `local/api_key/` 或环境变量，由程序读取 |
| | 把课程资料复制到仓库、网盘、聊天等公开位置 | AGENTS.md 写明（资料只在本机和已配置的模型接口之间流动） |
| | 删除或覆盖实验结果（使用 `--fresh`） | 交接文档写明。原因：第 1 轮结果因此丢失 |
| | 为了通过而跳过、放宽或删除测试和校验 | AGENTS.md 写明；验证者检查 |

**关于分支保护：** 暂不开启（见 1.3）。资料和密钥的隔离不依赖分支保护：它们在 `.gitignore` 里，任何分支都提交不进去。

## 5. 默认完成标准

写在 AGENTS.md，所有任务共用，不用每次写合同。

**所有改动：**

- 回复里给出实际运行的命令和输出摘要。没有运行的项写“未验证”和原因。
- 改动不超出任务范围。
- 提交信息写清改了什么，不加 AI 署名。
- 测试失败时，先判断测试表达的是需求（用户要求、接口合同、设计文档），还是临时限制或旧需求。前者改实现；后者与当前需求矛盾时可以更新测试，并说明改了哪个测试、依据哪条需求。任何情况下都不为通过而跳过、放宽或删除测试。

**鸿蒙端：**

- 构建通过。候选命令是 `ohpm install` 加 `hvigorw assembleHap -p buildMode=debug`；鸿蒙工程建好、第一次跑通后，把实际命令填进 AGENTS.md。
- 改界面时在 DevEco 模拟器上运行，截图存 `local/证据/`。
- 用了不熟悉的 ArkTS/ArkUI 接口时，在回复里给出依据（官方文档或 DevEco 的类型提示），不凭记忆。理由：计划书已经把“核对陌生 API”列为规则，ArkTS 是 AI 最容易编造的地方。
- 团队没有真机，回复里注明“未在真机验证”。

**后端：** 测试命令通过（后端开写时填入）。调用真实模型的改动写明用量。

**接口和数据结构：** 先走接口变更流程（6.4），Schema 校验通过。

**较大改动：** 在 `docs/实施记录/<日期>-<主题>.md` 记录修改与验证结果。

## 6. 任务流程

### 6.1 判断大小

| 小修 | 大任务 |
|---|---|
| 一个页面的样式、文案、交互细节；一个明确的 bug | 改接口合同或数据结构；同时涉及鸿蒙端和后端；新的页面流程 |
| 一句话说得清要什么 | 描述含糊，或有多种合理理解 |
| 一次会话能完成 | 要跨会话、要拆步骤或先调研 |

拿不准时按大任务处理，但合同可以写得很短。

### 6.2 小修

1. 读 AGENTS.md 的地图，只打开需要的文件。
2. 从 `main` 拉任务分支。
3. 实现。
4. 按完成标准检查，贴出结果。
5. 提交、推送、开 PR。
6. 不更新 STATE.md，除非产生了今后要遵守的决定或留下了没解决的风险。

### 6.3 大任务

1. 用 `docs/协作/任务合同.md` 写合同；描述含糊时先给人确认。
2. 在 STATE.md 自己工作线的「当前步骤」写上任务、分支和计划。
3. 分步实现；每个阶段只更新完成度，不追加过程。
4. 跑完成标准，贴出结果。
5. 改了接口合同或同时涉及两端时，交给另一个会话按 `docs/协作/验证者提示词.md` 审查。
6. 写实施记录；重写 STATE.md 自己工作线的条目。
7. 推送、开 PR，等人确认合并。

### 6.4 接口变更

这是鸿蒙端和后端能并行开发的关键。

1. 单独开一个 PR，只含 `schema/` 或 `docs/接口合同/` 的改动和样例 JSON。
2. 另一端负责人在 PR 里确认，然后合并。
3. 两端各自开分支实现。
4. 两端都用合同里的样例测试：后端的返回值过 Schema 校验；鸿蒙端用样例 JSON 渲染页面。

不允许在实现 PR 里顺手改合同。原因：两端并行开发，一端悄悄改了字段，另一端要到联调时才发现。

### 6.5 本地代跑

沿用现在的交接方式，把它固定成模板（`docs/协作/本地交接模板.md`）：

1. 设计方写交接文档，放在本地（原型目录或 `local/`）。
2. 代跑 agent 只负责运行和如实报告，报告写在本地。
3. 负责人把结论和数字写进仓库的实施记录或设计文档，不贴课件内容。

模板本身没有敏感内容，可以进仓库；填好的交接文档和报告留在本地。

### 6.6 设计文档的更新

设计文档只写当前结论和理由。实验过程和数字写进实施记录，设计文档里引用。已有的 `设计修订v2.md` 第 5 节可以在仓库同步完成后单独迁移，见 7.3。

### 6.7 交付时的回复

- 改了什么（一两句）
- 验证结果（实际命令和输出摘要）
- 没做到或没验证的部分，以及原因
- 需要人决定的事项

## 7. 状态与记录

### 7.1 STATE.md

指南要求“一个时间只有一个 agent 写 STATE.md”。本项目鸿蒙端和后端会并行，所以改成**按工作线分条**：

- 「当前步骤」和「下一步」按工作线各写一条（鸿蒙端、后端与 AI、设计与评测）。
- agent 只重写自己工作线的条目；「已做决定」和「风险」只改本次产生或解除的条目。
- STATE.md 的改动随任务 PR 一起合并，冲突在 PR 里由人解决。

其余沿用指南：

- **何时更新：** 开始或结束一个跨会话任务、做出今后要遵守的决定、出现或解除未解决的风险、合并到 `main`。普通小修不更新。
- **怎么更新：** 整体重写自己的条目，不追加；完成的内容移到实施记录，只留链接；不写提交哈希和构建号；全文约 40 行以内。
- **顶部注释：** 重复最关键的规则，因为 agent 打开 STATE.md 准备修改时最需要看到它。

### 7.2 实施记录

`docs/实施记录/<日期>-<主题>.md`，模板在 `docs/协作/实施记录模板.md`。同一天同一主题的追修，在文件末尾追加一节，不新建文件。

### 7.3 现有文档的迁移

- **已完成（2026-11-23）：** 原《进展总览》拆开：项目说明和目录进 README，当前状态和下一步进 STATE.md，已定设计、实验进度和未决问题成为 `docs/设计/设计摘要.md`。
- **未做：** `设计修订v2.md` 第 5 节（逐轮实验结果）移到实施记录，设计正文只留结论和链接。可以作为一个单独的文档任务。

## 8. AI 参与说明与提交署名

README 中加一节：

```markdown
## AI 参与说明

本项目使用 AI 工具参与开发。各 AI 在第一次参与、或参与内容出现新类型时，更新自己的那一行；不按任务逐条记录。

| AI 工具 | 参与内容 |
|---|---|
| Claude | 设计、文档 |
| Codex | 开发 |
```

规则：

- **每个工具一行，只改自己那一行。** 参与内容只写类型：开发、测试、文档、设计、审查、实验代跑；可以附一个范围，例如“开发（鸿蒙端页面）”。
- **只在第一次参与或出现新类型时更新。** 理由：如果每个任务都写，它会和 STATE.md 一样变成流水账；多个 agent 同时改同一张表也会频繁冲突。
- **提交信息不加 AI 署名**（不加 `Co-Authored-By` 之类的尾行）。有些工具默认会加，使用前在工具设置里关掉；关不掉时提交前删掉。

## 9. 多 agent 协作

- **一个任务一个分支，一个分支同一时间只有一个 agent 在写。** 分支名用 `<工作线>/<主题>`，例如 `harmony/upload-page`、`backend/plan-api`、`docs/contract-v0.3`。
- **交接以文件为准。** 上一个会话的结论写进 STATE.md、合同或实施记录，下一个会话读文件，不靠对话复述。
- **换工具接手同一任务时，** 先读 AGENTS.md、STATE.md、该任务的合同和最近的实施记录。
- **验证者和实现者分开。** 验证者给出 REJECT 后，由实现者修改，再交给验证者复查；不让实现者自己判断 REJECT 是否成立。

## 10. 暂不做，以及什么时候再做

| 项 | 现在 | 什么时候加 |
|---|---|---|
| 重试上限、失败分类 | 不写 | 发现 agent 在同一问题上反复折腾 |
| STATE.md、AI 参与说明的格式检查脚本 | 不写 | 写清楚的规则在 diff 里被反复违反；检查结构，不数行数或搜关键词 |
| CI | 先只跑后端测试和 Schema 校验 | 鸿蒙端在 CI 里构建要装命令行工具和 SDK，成本高，先用本地构建证据；PR 多到审查跟不上时再加 |
| 每个任务都写合同 | 不要求 | 只有大任务写 |
| 分支保护、各工具的权限配置 | 不做 | 出过一次直接推送 `main` 或其他未授权操作 |
